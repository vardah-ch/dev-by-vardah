Case 01 · Aug 2026 to now

Multi-town Real Estate ERP

One system for a developer running about 13 towns

  • In progress
  • Paid client work
  • Sole developer

The problem

Each town has its own landowners, plots, payments and expenses. The office needed one system where every town's records stay separate, while the owner can still see everything combined.

My role

I'm the only developer, from database design to the screens. I'm also a partner in the business: the owner brings in clients and I do all the software work.

Working today

  • Town-scoped views: open a town and see only its acquisitions and totals
  • Landowner ledgers showing what was agreed, what's paid and what's still owed
  • Land acquisitions with a draft and approval step
  • Payment recording by cash, cheque or bank transfer, with a note on every entry
  • Daily payments report filtered by date range and method

Architecture

  1. Browser · React + Vite + TypeScriptTown-scoped screens, forms with notes, filters
  2. API · Express + Node.js + TypeScriptLogin, validation, business rules, money totals
  3. PostgreSQL 15 in Docker · KnexDecimal money, transactions, forward-only migrations

Decisions & trade-offs

Reverse, never edit

WhyPosted money records stay as they are, so every change can be traced.

CostFixing a mistake means posting a reversing entry instead of a quick edit.

Money lives in the backend

WhyTotals come from the database, so every screen shows the same number.

CostEach new screen needs its own API work.

Forward-only migrations

WhyThe live database is never reset or rolled back.

CostA schema mistake is fixed with a new migration, not by editing an old one.

Rules before code

WhyAccounting rules are written down first. A security cheque isn't income, and moving cash between registers isn't an expense.

CostSlower start, fewer surprises later.

Next

Owner-managed roles and permissions, sold plots, resale and transfers, commissions, reports and backups. Each phase is tested and reviewed on screen before the next one starts.

Case 02 · Final year project · 2026

VAMORA

Virtual Alzheimer's Memory & Observation Recall Assistant

  • Two-person team
  • Frontend & database: me
  • University of Gujrat

The problem

People with Alzheimer's, the people looking after them and their doctors usually keep track of things in separate places. There was little software built for these patients specifically, so VAMORA gives each person their own view of the same care picture.

What it does

  • Role-based dashboards for Super Admin, Doctor, Caretaker and Patient
  • Mood tracking, plus AI-based mood detection to keep an eye on the patient's wellbeing
  • Appointment scheduling between patients and doctors
  • Cara, an AI chat companion powered by Llama 3 through the Groq API

My contribution

I handled the frontend and the database: the React screens for each role, and the PostgreSQL data model behind them.

Architecture

  1. Frontend · React + ViteSeparate dashboards per role, mood charts, chat with Cara
  2. API · Node.js + ExpressJWT login with bcrypt-hashed passwords, file uploads with Multer, calls to Groq
  3. PostgreSQL · SequelizeUsers, roles, moods, appointments

Team & links

Built with Amna Khan and supervised by Ms. Amina Tariq.

Case 03 · Product template

White-label Real Estate Platform

A public website and agency admin for the Pakistani market

  • Full stack
  • Next.js 16
  • Live demo

The problem

Every real estate agency needs the same things: listings, search, project pages and a way to handle inquiries. I built one codebase that any agency can rebrand, with no code changes.

What it does

  • Property search from the database by purpose, type, location and price, with sorting and pagination
  • Property pages with a keyboard-friendly photo lightbox, amenities and Call, WhatsApp and Visit actions
  • Projects, agent profiles, and a contact form that saves real inquiries
  • Owners can submit properties with photos, which go to a review queue
  • An admin dashboard with live stats, and editing for every listing, project and page
  • Prices in lakh and crore, areas in marla and kanal

Architecture

  1. Next.js 16 · React 19 · Tailwind CSS 4App Router, server components, server actions
  2. Auth & adminDatabase sessions in httpOnly cookies, hashed tokens, bcrypt passwords
  3. PostgreSQL · Drizzle ORMListings, projects, agents, leads and site settings

Decisions & trade-offs

Everything editable

WhyName, logo, colors and content live in the database, so one codebase fits any agency.

CostMore admin screens to build and maintain.

Nothing auto-publishes

WhyOwner submissions wait for review, and only published records are public.

CostSomeone has to review each one.

SEO built in

WhyPer-page metadata, a sitemap and structured data, so listings can be found.

CostEvery new page type needs its own metadata.

Local formats first

WhyBuyers think in crore and marla, so the data does too.

CostOther markets would need different formats.
